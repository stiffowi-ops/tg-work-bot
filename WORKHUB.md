# WorkHub — closed employee Mini App

Deploy branch main, Dockerfile, build context '.', port 8080.
Set BOT_TOKEN (the token of the bot that owns this Mini App), WORK_CHAT_ID (negative numeric group/supergroup ID, e.g. -1001234567890, example only), DATA_DIR=/app/data. Use a persistent writable volume at DATA_DIR owned by the runtime user (Alpine workhub). Run a single replica; the JSON store is atomic but not a shared database. Back up employees.json securely outside GitHub. Do not commit credentials or personal data.

Add the bot as an administrator in the work chat (minimum rights). Configure its Main Mini App in BotFather with the HTTPS hosting URL. This service does not run polling, and does not replace the existing Python bot. Telegram membership is checked on every personal API request for ordinary employees; a closed browser without signed initData cannot access employee data. Missing configuration and Telegram errors fail closed. Auth data expires after 12 hours; reopen in Telegram. No demo bypass on hosted app.

On first login the server creates an employee profile with the verified Telegram name and, if available, the user's profile photo fetched through the Bot API. Users may edit name, role, description, photo, status, project. Saved items and demo progress are stored for that account. The team contains users who have logged in and either have current membership or are explicitly configured app administrators. Bot API does not expose a complete ordinary member list. Real internal documents, production tests and notifications are not yet integrated; existing catalog is placeholder data. Team can link to Telegram username when present.

GET /api/health is public; GET /api/me, PUT /api/me and GET /api/team are protected. Validate member and non-member on actual Telegram clients before rollout. Automated Go tests use mocked Telegram calls and execute during Docker build. Keep repository private before adding corporate material.

## Project CMS V9
Set ADMIN_USER_IDS to comma-separated numeric Telegram user IDs. Explicitly configured app administrators can access the app independently of WORK_CHAT_ID, but must always present valid Telegram-signed initData (or an already authenticated media session). Ordinary employees must still be current members. Removing an ID from ADMIN_USER_IDS revokes this exception. BOT_TOKEN and writable profile storage are required for everyone. Invalid WORK_CHAT_ID blocks ordinary employees but no longer blocks configured admins. Startup logs report the configuration state without printing the token or admin IDs. Keep DATA_DIR=/app/data and mount persistent writable storage. The Go container serves only the Mini App, not the existing Python bot. Keep its deployment separate. On first save folders data/projects/calendar and data/projects/industry are created; files are stored under files/ using random IDs and content.json is atomically replaced. This version uses JSON (not SQLite), single replica only. Maximum upload is 128 MiB; proxy/hosting upload limits and timeouts must also permit it. Video MP4/WebM, images JPEG/PNG/WebP, documents PDF/DOCX/PPTX/XLSX/TXT. Admin uploads are not malware-scanned; scan trusted files before upload. Media access uses a short-lived HttpOnly Secure same-origin cookie plus current Telegram membership or explicit app administrator authorization; no public upload directory. Browser must accept cookies. Use HTTPS. Back up the entire persistent volume. Seed text/link/FAQ are editable examples; no corporate files are included.

Group diagnostics: in Admin, open the Telegram connection check. It uses getMe, getChat, getChatMember and getChatMemberCount; the admin's own membership is checked independently of their app-admin exception. Existing group members can sign in on first launch without any prior join event. The directory is registered profiles only, not a full Telegram roster. Unknown membership states and Telegram errors do not grant employee access. Migration IDs are reported, not automatically adopted. No polling, history scraping or additional token needed.

Deployment verification: GET /api/health returns the embedded release version (V9.7.1-content-builder). The same version is logged on startup, before access configuration. If it is absent after deployment, verify the host's checked-out branch and source revision; restarting the old image does not update the source.

Mobile layout: the scrollable shell and the bottom navigation occupy separate rows; the navigation no longer overlays the feed. Phone screenshots are viewport captures, not full-page composites. Use PORT supplied by the host if automatic, otherwise 8080, matching the proxy target. Preserve the existing persistent volume before deleting an old service.

Stability pass: mobile navigation and header are isolated from scrollable content; CMS prevents parallel client mutations and warns before leaving dirty forms. Browser fixture uses local TLS with a test-only certificate, matching production Secure cookie requirements. Keep HTTPS and never disable media access checks to troubleshoot delivery. Tests capture viewport screenshots before media checks. Real Telegram and Bothost acceptance remains required.

Media stability: recommend MP4 H.264 (AAC if audio), keep WebM support when the client supports it. Player displays network/decoder/format errors; the private media cookie renews on active project pages after 35 minutes through a signed, membership-checked POST. Browser tests use installed Google Chrome and inspect the existing MP4 codec, actual download bytes, HTTP range, playback and seeking. No authorization exception is introduced. Test success does not replace real-device acceptance.

Cabinet V9.6.1: existing editable profile and pinned project retained. Personal project folders and bookmarks use the published CMS material index, not demo files. Bookmarks persist per verified user in employees.json, without modifying legacy demo bookmarks. The authenticated bookmark endpoint validates published materials on add; deleted/unpublished items are omitted from the personal view. Training and notifications remain explicitly labeled demos. No additional environment variables.

## Storage contract (V9.6.3)

Production: use one Dockerfile and set DATA_DIR=/app/data in Bothost. Mount the existing persistent volume at exactly /app/data. Go resolves DATA_DIR once and passes the same storage configuration to employee profiles and CMS. Existing paths are unchanged: employees.json and data/projects/<project>/content.json plus data/projects/<project>/files/ relative to DATA_DIR. Back up the entire volume before deployment. An explicitly configured /app/runtime remains supported for an existing legacy deployment; do not change its mount or move files without a verified backup and a deliberate migration. There is no automatic migration or fallback to another directory. The Python polling bot remains a separate service.

## Content Builder V9.7
The existing ordered block array supports up to 200 mixed materials. Insert at any boundary; the upload checks the current revision and insertion anchor. Duplicates are independent unpublished drafts (file copies are independent, too). Preview shows published blocks using the employee rendering function. Existing document artwork and compact legacy links stay intact; links optionally use the same selectable cover artwork. No storage migration or change to authentication.

Links support compact, wide and minimal formats; new links default to compact with the globe (website) cover. Existing links without a style retain their previous appearance, and document covers are unchanged. Link-specific SVG assets are local and require no network.
